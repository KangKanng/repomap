## 1. 核心指标

| 指标 | 优先级 | 固定口径 |
| --- | --- | --- |
| Search Calls per Task | 主指标 | 每条任务显式Bash搜索子命令数，复用原AST统计器；同一动作中的多个grep分别计数 |
| Target Localization Cost | 关键辅助 | 首次成功通过工具读取官方目标代码区域时，累计搜索数和模型调用轮数；保存命中命令、消息/动作索引与源码证据 |
| Resolved Rate | 必须满足的约束 | 官方判分通过率，同时报告判题覆盖、重复间波动和运行错误；不以搜索减少掩盖成功率下降 |

Search Calls继续采用此前259→285的统计口径，保持可比性：包括文件定位、代码/测试搜索和日志过滤；不包括普通cat/sed、脚本内部检索和RepoMap内部扫描。
它衡量模型显式请求的搜索子命令，不能保证所有条件分支实际执行。原口径不静默改写；环境探索、维护操作等可在新增语义标签中单列。
包含搜索的工具动作数、总模型调用、输入/输出tokens、缓存及服务端已返回费用作为补充指标。
进行中的请求不计入完成结果汇总，费用总表当前只汇总已结束轨迹；不能把初始表中的0理解为尚在推理的请求免费。

完成后按20条任务等权、每任务3次重复等权计算搜索均值；同时输出每条任务的均值、标准差，以及每次完整重复的总体均值和这3个均值之间的标准差。
阶段性均值仅覆盖已经完成的有效推理，始终附完成分母。未完成、无效和超时运行不能当作0搜索的胜利。

每个正预算与同阶段、同任务、同重复编号的plain配对，报告搜索差值。
另提供interval减once的直接差值，以及两个阶段各自相对plain增量之差；后者有助于观察阶段漂移，不能消除全部服务端或顺序混杂。

成功率约束先报告观察到的差异；全量判题后标注该设置的观察成功率是否低于plain。
没有预设非劣效界值，也没有声称3次重复具有充分统计功效，因此“观察成功率未下降”仅支持候选结论，不等于证明真实成功率没有损失。

## 2. 定位成本的可核对实现

实现：[localization_metrics.py](../scripts/localization_metrics.py)。这是事后评测，官方补丁和参考区域均不进入推理提示词或Agent容器。

1. 从官方patch获取基线目标文件和旧侧hunk起点，读取已经归档的基线源码。
2. 在每个起点前后12行内提取足够长、在该文件中唯一的源码行；过滤短行、重复行和注释。保存为本轮`localization-reference.json`。
3. 在轨迹中寻找显式读取该文件的cat/sed/head/tail/grep等命令；支持明确的工作目录切换和Git show读取。
4. 对应工具动作退出码必须为0，且**模型实际可见**的工具输出包含参考源码片段。不会用仅存在于`extra.raw_output`而未展示给模型的内容加分。
5. 记录累计搜索数、模型调用轮数、动作编号、目标路径、基线行和命中片段。主表使用“含定位动作”的累计数，同时在JSON中保留严格位于该动作之前的搜索数。

计数边界是整个工具动作：一个动作含多个子命令时，不伪造其内部精确命中时刻。
仅列出目标文件名、地图包含文件、普通路径字符串命中、失败读取，均不足以认定已经读到目标代码。
这是一种可复核的“官方基线目标区域读取”操作性指标，不是直接测量模型心智中的定位。

任意Python脚本读取、复杂动态路径和替代正确修复路径可能无法自动识别。没有观察到时为`not_observed`，数值为null，不记0或自动判为定位失败。
新增文件没有基线代码，不计入这一读取参考；必要时结合任务要求补充经复核的替代目标，保持与官方口径分开。
主表同时给出定位可观察覆盖率；配对定位差值只对双方均可观察的记录计算，必须连同配对分母解释，不能将选择后的子集当作无偏总体结论。

## 3. 实验控制

- 两阶段都从项目`.env`读取同一模型，保存返回的实际模型标识；不修改模型、凭据或服务地址。
- 每次任务独立进程、独立容器、全新会话，保留mini原有累计历史，不复用上一重复的补丁或对话。
- Once：任务开始生成一次，排序仅用原始任务，`context_messages=0`；后续历史中保留同一张地图。
- Interval：每次查询刷新，排序使用原始任务和最近6条非系统、非地图消息。刷新后文本可能相同，并非每次必然得到不同地图。
- 因此once/interval对照包含刷新与上下文策略两个变化，不将差异全部归因于刷新频率。
- 每阶段的预算顺序按任务及重复编号轮换；并发保持2路推理、1路官方判题，阶段之间顺序执行。
- 预算之外的同阶段配置逐条合并后核对一致；扫描上限为20000文件、单文件1GiB、源码总量128MiB。
- 运行限制沿用250步、1200秒软时限、1380秒进程硬时限、单次任务费用停止阈值3美元。
- 推理与判题均断网；镜像固定到不可变ID，`--pull=never`。环境准备下载与正式推理/评测分开。

历史20条中Lucene缺少wrapper及全模块依赖。本次预热官方根`test`命令所需缓存，保留镜像已有的测试日志配置修改，校验预热前后源码差异一致。
正式启动前在断网官方流程中用历史补丁做独立预检；这些测试和候选补丁仅存在于预检临时容器，未烘焙进实验基线。
本次各条件都使用相同的修复缓存镜像，原有历史评分保持不变。

## 4. 保存每次请求的实际地图

[EnvLitellmModel](../src/mini_swe_repomap/env_model.py)将返回请求所使用的地图文本、消息位置和SHA-256保存在`extra.request_repository_maps`。
正常响应和格式错误响应均保存；plain保存空列表。未返回的请求仍可能缺少响应及费用信息，不据此估为0。

这是轨迹元数据。mini在准备后续API请求时去掉`extra`，因此不会把归档快照额外发回模型，也不新增地图消息。
已验证旧快照不会随地图替换而改写；以后可以按请求时间核对interval实际地图，不再用最后一张地图解释早期行为。

## 5. 自动队列与最终报告

入口：[run_repeated_budget.py](../scripts/run_repeated_budget.py)，报告器：[analyze_repeated_budget.py](../scripts/analyze_repeated_budget.py)。
驱动逐轮执行原有预算实验及官方判题，持续更新报告。每一轮完成后才开始下一轮，3轮once结束后自动转入3轮interval。
异常或未完成运行保留原记录，不挑选最佳重复，不静默覆盖已付费结果。
恢复使用`--resume`，核对原协议、准备文件与代码哈希；若已有驱动仍存活则拒绝再次启动，避免重复推理。

```bash
source .venv/bin/activate
REPEAT_RUN=benchmarks/results/once-interval-repeats-20261105T180350Z

# 正式运行；先前已启动时不要再次执行
python scripts/run_repeated_budget.py \
  --prepared "$REPEAT_RUN/prepared" --output "$REPEAT_RUN" \
  --collector-runtime /root/.cache/repomap-python/cpython-3.12.14-linux-x86_64-gnu \
  --phases once interval --budgets 0 1024 2048 4096 --repeats 3

# 只更新已有数据的报告，不发起推理或判题
python scripts/analyze_repeated_budget.py "$REPEAT_RUN"
```

## 6. 进一步解释搜索增加的步骤

已有40条once/plain轨迹中的544个搜索子命令已导出为 [搜索原因复核材料](../benchmarks/results/static1024-once-20261105T145121Z/search-cause-review/README.md)，总数与原统计一致。
当前语义标签尚未填写，不将模板当作已经完成的因果分析。

后续按每个子命令标注主要目的：定位、代码理解、验证、历史/环境参考、维护、未知，并结合实际首次读到目标的时间分段。
这样才能区分“定位确实更快但后续验证更多”“地图覆盖差导致重新定位”“已经定位却继续查上游与缓存”和重复实验中的正常路径波动。
同一命令重复不等于无效，需检查源码、环境或假设是否变化；judge可以辅助审阅，但引用、动作索引和结论仍需复核。

完成本轮后先检查三项核心指标是否一致：搜索是否下降、定位是否提前、成功率是否下降。
若相同once地图哈希下搜索差异仍很大，优先分析Agent路径波动；若定位改善而总搜索增加，继续分解理解与验证；若扩大预算后目标覆盖提高但定位不变，检查地图实际引用证据和噪声条目。
这些是待验证的诊断规则，不预先承诺更大地图或每轮刷新会减少搜索。
