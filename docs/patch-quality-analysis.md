# RepoMap 对生成补丁的可维护性与安全性：实际补丁审计

分析日期：2026-11-08。

后续已按要求使用 `.env-judge` 完成 full-once 组的 36 次可维护性评审，见 [LLM Judge 配对评估](maintainability-judge.md)。

**现有结果支持 RepoMap 帮助代码定位，但没有证明它能稳定提高补丁的可维护性或安全性。** 个别补丁更集中，也有修改范围扩大、遗漏边界的反例。本次还实际复现了一个官方判题通过的地图组补丁在空参数下栈溢出的问题。

这里评价的是“模型在带 RepoMap 上下文时生成的 patch”。RepoMap 本身输出路径和符号索引，最终补丁仍由 mini-swe-agent 调用模型生成。结论适用于本仓库的适配实现、任务和模型，不能外推到所有 RepoMap 工具。

## 样本与方法

- 主样本：[480 次重复实验](final-experiment-analysis.md)，20 个仓库各 1 条任务，once / interval 两阶段，预算 0 / 1024 / 2048 / 4096，各重复 3 次。实际提交 471 份补丁。
- 补充样本：[full-once 20 次实验](full-once-experiment.md)，实际提交 18 份补丁，复用预先选定的 once / repeat-01 / plain；这是历史对照。
- 合计 500 次尝试、489 份非空补丁。读取轨迹中的 `info.submission`，解析每个 diff，并对全部 489 份用 `git apply --numstat` 交叉核对文件数和增删行数；此命令仅统计，不应用补丁。
- 定量统计覆盖全部上述样本；语义审阅包含全部 18 份 full-once 补丁，以及围绕输入校验、递归、整数宽度、panic 边界和修改范围挑选的重复实验补丁。安全样本按问题选取，不是随机漏洞抽样。
- 补充引用已有初次 once 实验中的 fmt / Caddy 对照。这些旧样本不混入新的 500 次统计。

“源码增删行数”是源码路径中的新增行加删除行，含注释、空行和源文件内嵌测试。测试目录/文件名按路径识别，未用 AST 分离 Rust 的 `mod tests`。没有把 diff 长度当成圈复杂度或可维护性评分。

配对只包含同阶段、同任务、同重复编号两侧均正常提交的运行；失败/无补丁不按零行计算“精简收益”。95% 区间按任务整簇重采样 10,000 次，保留簇内重复，种子 20261108；是未做多重比较校正的探索性区间，独立任务仍只有 20 条。

**所有增删行数差异区间均包含零。** 较小预算、较大预算和完整地图都没有形成一致的精简趋势。重复实验地图条件共有 110/347 个有效配对的源码改动完全相同；这些配对复用了 plain 基线，不是 347 个独立任务。

修改文件数也不能概括为普遍减少：once-1024 从 1.44 降到 1.23，只有 4/57 对减少，变化集中在 bat 和 Tokio；interval-1024 从 1.42 增到 1.54。full-once 从 1.50 增到 1.83，其中 Tokio 单条增加 7 个文件，bat 少 1 个，其余 16 条不变。平均值容易由少量多文件任务主导。

只看两组均通过的子集，once-1024 增删行数从 15.17 降到 12.78，46 对的区间为 [−4.88, −0.28]。这可以描述部分成功补丁较集中，但按成功结果筛选有选择偏差，也没有在其他预算复现，不能据此宣称总体可维护性提升。

与官方补丁比较的额外/缺失源码路径也已导出，但只用于找审阅对象。例如 Tokio 可以在共享内部类型或公共网络类型上实现同一需求，两种方案的文件集合本来就不同；“官方补丁没改这个文件”不等于该修改错误或多余。

### 能说明问题的具体补丁

| 案例 | 实际代码差异 | 对可维护性的含义 |
| --- | --- | --- |
| 初次 once / fmt | plain 在修复对齐时还改变 zero-fill 条件，引入 `PrintfTest.ZeroFlag` 回归；地图组只保留左对齐修复并通过 | 有较集中、避免无关回归的正例；不能仅凭一次结果归因地图 |
| 重复实验 / Caddy | interval-1024 三次均未通过，同阶段 plain 三次均通过；例如 repeat-01 地图组额外把 `default_bind` 特例加入 `httptype.go`，涉及 3 个文件 | 地图没有保证改在合适的抽象层，也没有保证回归覆盖；评分差不能单独确定每次失败根因 |
| full-once / Tokio | 在 8 个文件、9 个公共类型上复制 18 个 marker trait 实现；历史 plain 在 `Registration` 单文件实现，官方参考在 `PollEvented` 单文件实现 | 都能满足当前判题，但分散声明增加今后新增类型时重复维护和遗漏的机会；完整地图没有自动促成共享实现 |
| full-once / SymPy | 对异维点直接抛 `ValueError`，并将检查扩展到 `taxicab_distance`、`midpoint`、`dot`，共 4 个 hunk | 需求是补齐维度后得到 `sqrt(5)`，补丁误读需求且扩大行为变化，原官方评分失败 |
| Flask / Redis | 各 25 份正常提交的补丁，源码改动分别完全一致 | 搜索和过程可以不同，但这两条任务没有产生额外补丁质量收益 |

## 安全性：未证明增益，并实际复现一个边界回归

### bat：通过官方测试的地图组补丁可被空后缀触发栈溢出

定位到 `interval / repeat-02 / 1024 / sharkdp__bat-1892`。该补丁把用户后缀接入 `try_with_stripped_suffix`，但没有过滤空字符串。空后缀匹配任意文件名，剥离后文件名不变；语法检测的递归调用因此不能前进。同轮 plain 则明确过滤 `suffix.is_empty()`。

为避免仅凭静态模式判断，在原固定镜像中分别应用两份原始 patch，使用 `cargo build --offline --bin bat` 编译，运行同一真实 CLI。镜像为 `sha256:5d2de1e58584042fa687ba92e2d875f29232d682dca095547803db21e6211e47`，容器 `--network none`。测试文件使用无法识别语法的扩展名，内容为 `{"hello": 1}`。

```bash
bat --no-config --paging=never --color=always --style=plain \
  --ignored-suffix '' /tmp/repomap-probe.auditunknown
```

| 运行 | 原官方评分 | 本次空后缀用例 | 非空 `.example` 对照 |
| --- | --- | --- | --- |
| 同轮 plain | 通过 | 正常退出 0 | 正常退出 0 |
| 同轮 interval-1024 | 通过 | `SIGABRT`，Python 记录退出 −6，stderr 报 stack overflow | 正常退出 0 |

强制 `--color=always` 是触发语法检测的必要测试条件；本次先用 `--color=never` 时两份补丁均正常退出，已保留该控制结果，没有把未触发目标路径的运行当成安全证明。

这是已复现的可用性问题。触发者需要能提供该 CLI 参数或配置；没有据此认定远程可利用、任意代码执行或整个 RepoMap 系统存在同一漏洞。新增特性要求中未要求空后缀，官方判题通过也未排除这个边界问题。

审阅这条任务的 24 份正常提交：5 份 plain 都有空后缀守卫，19 份地图条件补丁中 18 份有守卫，1 份是上述漏检。这个小样本不用于估计一般漏洞率，也不能推出地图普遍降低安全性；它足以反驳“有地图且判题通过就能保证安全”。

证据：[实际运行日志](../benchmarks/results/patch-quality-20261108/probes/bat-runtime.jsonl)、[关闭颜色的控制结果](../benchmarks/results/patch-quality-20261108/probes/bat-runtime-color-never.jsonl)、[复现程序](../benchmarks/results/patch-quality-20261108/probes/probe_bat.py)、[地图组原补丁](../benchmarks/results/patch-quality-20261108/probes/bat-interval-r2-b1024.patch)、[plain 原补丁](../benchmarks/results/patch-quality-20261108/probes/bat-interval-r2-plain.patch)。复现使用临时容器，没有修改原镜像、原评分或原推理轨迹。

### 其余安全相关代码没有显示独立的地图收益

| 任务 | 实际补丁观察 | 能支持的结论 |
| --- | --- | --- |
| Django URLValidator | 24 份正常提交只有两种字符类，分别排除 `\s:@/` 和额外排除 `?#`；plain 和地图条件都出现变体，全部正常提交均通过本任务判题 | 确实修复了任务中的 URL 校验问题，但没有证明地图带来额外校验收益；没有独立恶意输入集或复杂度测试 |
| Redis XTRIM | 25 份源码补丁完全相同：两处 `int` 改成 `int64_t` | 对任务中的截断/错误裁剪有修复作用，收益不是地图组独有 |
| Gson JsonTreeReader | 25 份补丁均在根节点弹栈后的访问上加入 `stackSize > 0` 守卫，写法略有不同 | 减少这条任务中的越界异常；Java 数组异常不能直接解释成 C/C++ 式内存安全漏洞，也没有地图独有提升 |
| Tokio unwind traits | 存在对 `PollEvented`、`Registration`、公共网络类型及底层同步类型添加 trait 的不同方案；部分地图补丁对泛型 `Mutex<T>` / `RwLock<T>` 广泛声明 | 通过 trait 断言不能替代审阅 panic 后的不变量。扩大声明范围是需要审阅的点，尚未证明其产生实际漏洞 |
| Axios body limit | 按原需求在未配置有限上限时向 follow-redirects 传 `Infinity` | 属于恢复明确约定的行为；不能把它计成“安全加固”，也不能脱离用户配置直接标为漏洞 |

Rust 官方文档说明 `UnwindSafe` 是用于提醒 `catch_unwind` 调用者关注逻辑不变量的 marker trait，并不是 `unsafe trait`；不应把添加这个名称的实现直接计成内存安全提升。[Rust 官方说明](https://doc.rust-lang.org/std/panic/trait.UnwindSafe.html)

没有用简单关键字扫描的“零告警”作为安全结论。对于这些跨语言小补丁，本次得到的是若干已核对的修复与一个已复现的回归，没有完成所有补丁的漏洞审计。

## 目前数据不能回答的部分

原任务明确禁止修改测试、提交复现脚本。因此 489 份补丁均未修改按路径识别的测试文件，不能据此判定模型“没有写测试”，也不能把测试文件数量作为地图的负面指标。部分 Rust 源文件内嵌测试的调用适配仍计入源码路径增删行数。实际执行了什么测试要看轨迹和日志。

原官方 `resolved` 只证明规定的任务测试满足；它没有直接衡量可读性、抽象边界、未来变更成本或漏洞数量。重复样本的成功率也没有证明非劣效；Gson 有一条目标测试未执行的环境未决，保留原评分，见[最终分析](final-experiment-analysis.md)。

完整地图列出更多符号，没有因此变成编译器级调用图、污点分析或安全审查。最终地图还可能已吸收模型修改后的信息，不能拿它与最终补丁重叠作为“地图引导了正确修复”的证据。

## 若继续验证质量，应测什么

1. 在同任务中交错运行 plain / budget / full，增加独立任务，按任务簇统计；预先固定样本和复跑规则，保留所有失败。
2. 对方案隐去是否使用地图，再审阅是否复用共享抽象、是否遗漏调用点、是否有无关行为变化，并记录分歧；不把行数或与官方 diff 的距离直接当质量分。
3. 在补丁质量实验中单独允许提交回归测试，比较新增测试能否发现其他候选补丁的错误，而不是只统计断言数量。
4. 增加独立边界测试，例如空后缀/重复后缀、URL 认证字段分隔符、64 位 ID 极值、根节点弹栈、panic 后状态；对适用语言再加静态分析或模糊测试，区分原有问题与补丁新增问题。
5. 预先规定“更少新增缺陷且修复成功率不下降”的约束，再比较维护成本和搜索成本。目前的实验更适合评价定位辅助，尚不足以支持代码质量承诺。
